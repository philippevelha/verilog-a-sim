verilog-a-sim — release log
===========================

Versioning, from 0.9.0 onward:

  * A feature, or anything that changes behaviour, bumps the patch:
    0.9.0 -> 0.9.1 -> 0.9.2 -> ...
  * A pure fix, or docs/process with no behaviour change, appends a build digit:
    0.9.8 -> 0.9.8+1 -> 0.9.8+2. Spelled `+N` and not `0.9.8.1` because Cargo versions
    are semver and a fourth numeric component is rejected outright (verified: `cargo
    metadata` refuses 0.9.7.1 and accepts 0.9.7+1).
  * Each bump gets a dated entry below with a sentence or two saying what changed.
  * 1.0.0 is reached when the remaining 1.0 blockers (see the "Road to 1.0" list at
    the bottom) are closed. Until then the version stays in the 0.9.x range.
  * The version lives in the workspace Cargo.toml (`[workspace.package] version`);
    every crate inherits it with `version.workspace = true`. Bump both together —
    the number in this file and the one in Cargo.toml must always agree.

Newest first.


0.9.14+1 - 2026-09-11
---------------------
Docs only: the user-facing workflow is written down. `docs/workflow.md` says what a simulation
needs (a `.va` component, a `.net` deck as the testbench, one `va-cli sim` call), walks the
half-wave rectifier through it with the real output of this version (718 timepoints, V(out)
peaking at 4.304 V = 5 V crest minus a diode drop, decaying to 2.076 V at t=5 ms), and states
the thing a newcomer gets wrong: there is no separate elaborate/compile step -- `sim` elaborates
in memory every run, and `check` is a diagnostic, not a prerequisite. README gained a
"Running a simulation" section pointing at it.

  The document is explicit that this is the v0.9.x workflow, driven from source via `cargo
  run` on the development machine. **At 1.0 the deliverable becomes the compiled executable**,
  and the executable must be tested on several different platforms (different computers,
  different operating systems) before the version is claimed. That is a new 1.0 blocker,
  added to "Road to 1.0" below; it was implicit in the pure-Rust/no-native-link rule and is
  now stated.

  Measured at this version: `cargo run -p va-cli -- sim circuits/rectifier.net --model
  models/diode.va --tran` completes; `cargo test --workspace` 764 passed / 0 failed;
  `cargo xtask validate` 27 checked, 0 failed, convergence 27/27 -- no code touched.


0.9.14 - 2026-09-10
-------------------
Iteration statements now carry the restriction that defines them. `while`/`repeat`/`for` have
run since T2.2; what was missing was LRM 4.5.15 ("Analog operators are not allowed in the
repeat, while and non-genvar for looping statements") and 5.9's list for the same three loops
(no analog filter functions, no event control statements, no contribution statements).
`token-reference.md` had carried the 4.5.15 half as a stated gap since the token audit.

  The LRM's stated reason is literally true here. An operator's state is one slot per `ExprId`
  -- `va_codegen::lower::collect_stateful_calls` walks the *expression arena*, not the statement
  tree -- and a monitored event is one `Module::event_sites` entry registered once at
  elaboration. Neither is per-trip, so a loop running one call site N times does not give it N
  histories: it pushes N signals through one, and every trip but the last is overwritten before
  the step ends.

  **One corpus file was doing exactly that.** `external/verilogaLib-master/adc_16bit_ideal.va`
  writes `for (j = 0; j < 16; j = j + 1) V(out[j]) <+ transition(out_val[j], ...)` over an
  `integer j`: sixteen bits, one `transition` call site, one filter state thrashed sixteen times
  per timepoint, each bit's value depending on the ones evaluated before it. **Corpus 113/132 ->
  112/132** (94/99 self-contained) -- the v0.9.1 shape of drop again, a file that had only ever
  been *building*, and one that started being wrong the day `transition` stopped folding and
  started carrying state. Its fix is one word, `genvar j`, which the diagnostic names; a test
  pins that the advice works, by asserting three trips of a genvar loop unroll into three
  distinct `Builtin::Ddt` arena entries with a state slot each.

  **Enforced narrower than the LRM lists, deliberately.** The line is "does this pipeline key it
  by call site", not "does the LRM list it". Rejected: `ddt`, `idt`, `transition`, `slew`,
  `absdelay`, the four `laplace_*`, the four noise builtins, and `@(cross/above/timer ...)`;
  `ddx` excluded exactly as the LRM excludes it. Allowed knowingly: a plain contribution in a
  runtime loop, and `@(initial_step)`/`@(final_step)`, which lower to a global flag rather than a
  registered site -- N trips contribute N times and read the same correct flag, which is what the
  source says. A scan of all 171 `external/` files found exactly one contribution inside a
  runtime loop (the `adc` line above, refused for its filter anyway), so enforcing 5.9 literally
  would have cost nothing measurable and bought nothing.

  **The check reads the lowered IR, not the source spelling.** `transition`/`slew`/`absdelay`/
  `laplace_*` used to fold to a stateless value at elaboration, where a loop genuinely could not
  corrupt them; a rule written against source spellings would have been right when written and
  silently wrong from the day those operators grew state. Reading the IR covered them the moment
  they did.

  **Raised as an elaboration error, not a `Refusal`** -- the one call with a plausible
  alternative. A refusal means "valid Verilog-A that this simulator declines"; this source is not
  valid Verilog-A, and saying "my model is wrong" is the correct next step for the reader.

  Still not enforced, and still stated: 4.5.15's first bullet (operators under a
  solution-dependent `if`/`case`/`?:`), beyond the narrow escaping-`ddt` case `va-codegen`
  already catches. One `va-cli` test moved to assert the frontend's message, since the loop half
  of that codegen check is no longer reachable from source. Also checked against the LRM and left
  alone: `forever` is correctly refused -- `analog_loop_statement` (A.6.8) is `repeat`/`while`/
  `for` only, and `forever` is digital-only, excluded by Annex C.7.

  Measured at this version: `cargo test --workspace` 764 passed / 0 failed (was 756; 8 new tests
  in `va-frontend`), `cargo xtask validate` 27/27 with convergence 27/27 (100.0%), `va-cli check
  external --codegen` 112/132.


0.9.13 - 2026-09-09
-------------------
`$limit`'s model-declared junctions. The value still folds; the junction the access names no
longer does. Closes the third expired-premise item -- and only the half of it that had expired.

  `$limit(V(bi,ei), "pnjlim", VT, Vcrit)` is the corpus's most-used construct (10 files, 72 call
  sites) and it folded away entirely. The *value* fold was right and stays: a converged Newton
  solve is a fixed point of the unlimited equations, so a limiter reshapes the iteration path and
  never the answer, and the stateless `load` ABI holds no previous iterate to limit against.
  What was wrong was throwing the rest away with it. The access argument is not a value at all --
  it names a junction authoritatively, and that is precisely the question `va-codegen` had been
  answering by guessing.

  Its guess was per module and coarse by construction: "this source contains an `exp`, so every
  one of its nodes is a junction." For a compact BJT that is every external terminal behind a
  series resistance, plus the thermal node -- none of which have an exponential across them, all
  of them throttled to roughly vt*ln(...) ~ 0.2 V per Newton iteration.

  So elaboration records both endpoints of each limited branch in
  `va_ir::Module::limited_junctions` (an additive Interface alpha change, sec 6 -- see
  `docs/interfaces.md`'s 2026-09-09 revision), `va-codegen` reports exactly those through
  `ModelInstance::unknown_is_junction`, and `va-core`'s existing `limit_junction` clamp lands
  where the model asked. **Both endpoints**, because `pnjlim` clamps a potential difference while
  the solver limits per unknown; limiting only `bi` of `V(bi,ei)` would leave the difference free
  to take the step the model asked to have bounded. Interface beta is untouched:
  `unknown_is_junction` already existed and already had the right shape, it was only being told
  a guess.

  **A declaration is trusted exclusively, and that is a real trade.** A module that writes at
  least one `$limit` has enumerated its junctions, so the nodes it left out are reported as not
  junctions -- where the blanket guess would have covered them. A model that limits one junction
  and leaves a second exponential unlimited now gets exactly what it asked for. That is the LRM's
  own division of labour, the fix for such a model is the `$limit` it omitted, and no converged
  answer moves either way. A module that writes no `$limit` keeps the guess unchanged.

  **Stated limitations, all costing iteration path and never the answer.** The algorithm name is
  not honoured: `"pnjlim"`, `"fetlim"`, `"typedpnjlim_new"` and any user-written limiter all get
  `convergence::limit_junction`'s `pnjlim`, at `VT_NOMINAL`/`default_vcrit` rather than the
  model's own `vt`/`vcrit` arguments, which are still parsed and never evaluated. A `$limit` on a
  **flow** access declares nothing -- a voltage-shaped clamp on a current unknown is the exact
  bug `unknown_is_junction` was introduced to stop -- and folds as before.

  Gated by `a_model_declared_junction_limits_that_node_and_leaves_the_others_alone`, which
  compiles one model twice, with and without the `$limit`, in a circuit mixing an exponential
  junction with a linear pair driven at 100 V. Declared: it converges. Without: the per-module
  guess claims the 100 V node and Newton's budget runs out. Checked in both directions, not
  assumed -- the failing half is asserted, so the test cannot pass by being decorative.

  Also fixed here, being the premises this invalidated: `va-core/src/convergence.rs`'s header
  still described the clamp as blanket over every unknown (untrue since `unknown_is_junction`
  landed in 2026-07, and doubly so now), and `va_abi::ModelInstance::unknown_is_junction`'s own
  doc still said a generated model opts in "exactly when its source contains an exponential".

  Cost: none measured. `cargo xtask validate` is byte-identical across all 27 gates against the
  previous commit (diffed, not assumed -- no zoo model writes `$limit`, so the fallback path is
  what every gate exercises), and the corpus is steady at 113/132. The three golden-IR snapshots
  gained one `limited_junctions: []` line each and nothing else.

  756 tests, 27/27 golden circuits, corpus 113/132 (95/99 self-contained), clippy and fmt clean.


0.9.12 - 2026-09-07
-------------------
`$simparam` is answered for real, and answered **during the solve** rather than at elaboration.
Closes the second of the remaining expired-premise items ("v0 has no simulator-parameter store").

  The premise expired at the *evaluation* boundary, not at elaboration, and that distinction is
  the whole design. `iteration` changes on every Newton iteration; `gdev` changes on every
  homotopy stage; the tolerances belong to the solve's configuration, and one module is solved
  many times under different configs. So the values ride `va_abi::AnalysisCtx::sim`
  (`SimParams`, an additive Interface beta change) and are read at load, exactly as `ddt_coeff`
  is. The roadmap's own note said this would need "those values to reach elaboration" -- that
  would have been the wrong fix, and is corrected there now.

  A `parameter` context still folds to the stated default, deliberately: a parameter's value is
  fixed at elaboration by definition and cannot hold a per-iteration quantity.
  `external/bsim6.0.va`'s `parameter real GMIN = $simparam("gmin", 1.0e-15);` keeps working and
  keeps meaning what it meant.

  **Five names are known**: `gdev`, `iteration`, `sourceScaleFactor`, `abstol`, `reltol`. Every
  other name is *unknown*, which is a defined LRM outcome rather than a gap -- it returns the
  query's own default, or, with no default, is refused (LRM 9.18) with the list of names that
  would have worked.

  **`gmin` is deliberately NOT one of them, and this is the correction worth reading.** The first
  cut of this work treated `gmin` and `gdev` as one quantity. The LRM separates them: `gmin` is a
  permanent conductance floor across every nonlinear branch, `gdev` the additional conductance a
  homotopy adds. This engine has only the second, and only while gmin stepping is on, which it is
  not by default. Grepping the corpus decided it rather than argument: **21 occurrences** write
  `$simparam("gmin", 1e-12)` or `$simparam("gmin", 0)` and use the fallback to decide how much
  conductance to add themselves. Answering "known, and it is zero" would have been true of the
  solver and silently stripped the 1e-12 shunt those models add for their own conditioning -- a
  real change to a circuit, made on a technicality. Leaving the name unknown returns each model
  its own fallback, which is both what they mean and what they got before.

  **A correctness consequence in the transient loop, not just a plumbing one.** A model may
  legitimately key its behaviour on the iteration number, so the post-accept evaluation that
  *commits* state has to be made at the iteration the solve actually converged at -- committing
  at 0 would write history from a different model than the one that produced the accepted
  solution. `newton_step` therefore returns a `Solved { x, iterations }` and the commit and
  final-step-probe assembles use it. This is the `StateBuffers` commit-matches-solve invariant,
  extended to a channel that did not exist when it was written.

  Gated by `simparam_iteration_advances_during_a_transient_solve`, whose model is a 1 Ohm
  resistor on iteration 0 and a 1 kOhm one thereafter, so a frozen iteration number lands on an
  RC time constant 1000x wrong. Checked that it discriminates by freezing the number and watching
  it fail, not by assuming. Also `newton_config_and_simparams_agree_on_tolerances`, which pins
  the tolerance constants `va-abi` must duplicate (it is a leaf crate and cannot depend on
  `va-core`) to `NewtonConfig`'s.

  No behaviour change anywhere it is not used: `cargo xtask validate` is byte-identical across
  all 27 gates against the previous commit, and the corpus is steady at 113/132.

  752 tests, 27/27 golden circuits, corpus 113/132 (95/99 self-contained), clippy and fmt clean.


0.9.11 - 2026-09-07
-------------------
Instance multiplicity: a deck line's `m=` now means something, and `$mfactor` reports it. Closes
the first of the four remaining 1.0 blockers' expired-premise items -- `$mfactor` folded to `1.0`
because "v0 has no netlist-driven instance parameters", a premise that expired when a device line
gained `name=value` overrides.

  `$mfactor` lowers to `va_ir::Builtin::Mfactor` and is answered at the **instantiation
  boundary** (`Module::multiplicity`), not folded at elaboration -- a module is elaborated once
  and instantiated many times, so no instantiation-dependent value folded there can be right for
  all of them. Same shape `$param_given` took for the same reason.

  **The scaling is applied outside the instance.** LRM 6.3.6's guarantee is that an instance with
  multiplicity m behaves exactly as m identical instances would, and scaling a *stamp* is
  literally that: `va_abi::Multiplied` wraps the built instance and scales residual, Jacobian,
  charge, charge Jacobian, AC excitation, and noise power. One rule for hand-written and
  generated models alike, and it makes two LRM sub-rules fall out rather than needing code:
  a flow probe reads the per-device value (the internal branch unknown is unscaled), and a
  voltage-source-shaped model's constraint row is multiplied through by m, which is the same
  equation with the same root while its KCL entries deliver m times the current.

  Noise power scales as **m, not m^2**: m parallel devices' noise currents are uncorrelated, so
  powers add. Scaling amplitude would be the answer for perfectly correlated sources - the wrong
  physics, and silent, since both produce a plausible spectrum.

  **`m=` does not always mean multiplicity, and that is deliberate.** In the corpus `m` is
  overwhelmingly the junction *grading coefficient*: `external/diode.va`, `diode_basic.va` and
  `angelov_gan.va` each declare `parameter real m = 0.5`. Silently reinterpreting `m=0.5` on such
  a line as "half a device in parallel" would be exactly the class of wrong answer this project
  refuses to produce. So `m=` is the multiplicity **only when the model declares no parameter
  named `m`**, `mult=` is always the multiplicity, and a model declaring `mult` makes the line
  ambiguous and refuses it. No existing deck changes meaning.

  The LRM asks a simulator to warn about double-scaling (6.3.6), and its own two examples are the
  specification, so they are the test: `badres` (`I <+ V/r * $mfactor`) is caught, `parares`
  ($mfactor read in a condition only) is not. Measured on badres with `m=3`: 36 A where 12 A is
  right - exactly m^2, so the warning earns its place. Warning rather than refusal, per the LRM's
  wording and because the model is correct at the default m=1. Stated limit of the *detection*:
  a model that launders `$mfactor` through a variable first slips past, which costs a warning,
  not a wrong answer.

  Not implemented, stated: 6.3.6's rule 4 (potential-referred noise power divided by m) has no
  channel -- `NoiseSink` carries only current sources -- and rule 5 (propagation into
  instantiated submodules) has no inner instance to reach, submodules being flattened by the
  frontend before an instance exists. Built-in R/C/D/V deck lines do not take `m=` yet; this is
  for `X` lines placing a Verilog-A model.

  Costs nothing where it is unused: `Multiplied::wrap` returns the instance untouched at m = 1,
  so a deck with no `m=` is bit-identical -- verified by diffing `cargo xtask validate` against
  the previous commit, all 27 gates byte-for-byte. The one `va-ir` field moved the committed
  golden IR by one line per zoo model, as expected.

  748 tests, 27/27 golden circuits, corpus 113/132 (95/99 self-contained), clippy and fmt clean.


0.9.10 - 2026-09-07
-------------------
Every refusal now says **what** was refused and **why**, in one shape, from whichever layer
raised it. Asked for directly: a user hitting a refusal needs to know what went wrong and why,
and until now the answer depended on which layer said no.

  The worst of it was a mislabelling. A frontend refusal arrived as

    Error: parse error: at preprocessed line 7, column 7 (`@(final_step("tran")) ...`): this
    form of ... is not supported: ..., found Some(Keyword(Keyword("final_step")))

  - one unbroken line, opening with `parse error`, closing with a debug-formatted token. Both
  halves actively mislead: `parse error` says *your source is malformed* when the truth is the
  opposite (the source is valid Verilog-A and this simulator declines to pretend to run it), and
  the `found ...` tail is the shape of an unexpected-token diagnostic, so a correctly spelled
  construct read as a typo. That distinction is the whole point - "my model is wrong" and "this
  simulator will not run my correct model" call for completely different next steps.

  `va_frontend::Refusal` now carries the four things a reader needs, and refusals are a distinct
  `FrontendError::Refused` rather than a `Parse`:

    [va-cli] refused: `@(final_step ...)` in a form this engine does not honour
    [va-cli]   where:    at preprocessed line 7, column 7 (`@(final_step("tran")) g = 1.0;`)
    [va-cli]   why:      discarding the trigger would run the body at every solve point instead
    [va-cli]             of when the event fires. For the analysis-filter form that is sharper
    [va-cli]             still: the filter says "not in this analysis", so dropping it runs the
    [va-cli]             body precisely where the model excluded it - wrong in every analysis
    [va-cli]   instead:  write the bare `@(final_step)`, or an `or` list of bare
    [va-cli]             `initial_step`/`final_step`; both are honoured
    [va-cli]   tracking: docs/roadmap.md, section "Analog events"

  All three layers that can refuse go through it: `va-frontend` (parse-time construct
  refusals), `va-codegen` (`CodegenError::Unsupported` - its messages already state their reason,
  so its `why` line says where to read it rather than inventing a second one), and `va-cli`'s
  transient-analysis gate, which refuses whole *models* and previously printed in a shape of its
  own. `refused:` is a deliberately greppable marker: "which constructs did this simulator
  decline, and why" should be answerable over a captured log.

  **A wrong `what`, found while testing this.** A buried `absdelay` was refused with a message
  naming `laplace_*` - the recognizer covers both and only the filter was named, so a user who
  wrote `absdelay` was sent looking for a filter they had never written. `contains_laplace_call`
  became `buried_frequency_domain_call`, returning which construct it found. A refusal that names
  the wrong construct is worse than a terse one.

  In `check`, a refusal's fields print to **stdout with the rest of the listing**, not to stderr:
  splitting a verdict from its reason across two streams is how the reason gets lost the moment
  anyone redirects the output to a file. In `sim`, `main` now renders a refusal itself and
  swallows the anyhow default, so the block is not also flattened onto one `Error:` line.

  Gated by `every_refusal_says_what_was_refused_and_why`, which checks all three layers together
  - the failure mode is one drifting back to a bare sentence while the others stay labelled, and
  no per-layer test would see that - and by `an_ordinary_error_is_not_mistaken_for_a_refusal`,
  because telling a user their correct model was declined when they merely mistyped sends them
  exactly the wrong way.

  Not covered: `FrontendError::Elaborate` refusals still print as plain elaboration errors. They
  state their reason inline and are not mislabelled, so they were left rather than churned; the
  `Refusal` shape is there when one of them earns it.

  739 tests, 27/27 golden circuits, corpus 113/132 (95/99 self-contained), clippy and fmt clean.


0.9.9 - 2026-09-07
------------------
Closes a hole 0.9.8 opened, and corrects a claim 0.9.8 made. **0.9.8's entry said compound
triggers "remain refused". They did not.** A trigger naming a step-scoped event that was not
exactly `@(initial_step)`/`@(final_step)` fell straight through to the discard path and ran its
body at every timepoint -- the same wrong-answer-not-missing-feature defect 0.9.1 was written to
remove. Verified before fixing, not assumed: `@(initial_step or final_step)`,
`@(final_step("tran"))` and `@(initial_step("dc"))` all compiled to an unguarded body.

  Worse, 0.9.8 *caused* half of it. `va-cli`'s transient gate matched on the trigger's **name**,
  so `@(final_step("tran"))` and `@(final_step or ...)` had been refused in transient purely as
  a side effect of `final_step` being on that list. Removing the name -- correct for the bare
  form, which is now implemented -- silently reopened the other forms. The `@(initial_step ...)`
  forms had never been covered by anything.

  The rule this earns, and the reason it is in the log rather than only in the code: **when a
  construct graduates from refused to implemented, check the refusals keyed on its name, not
  just the ones keyed on its behaviour.** 0.9.3 recorded the behaviour-keyed version of this
  trap ("check what else was riding on that refusal") and it recurred anyway, one layer down.

  What now happens, with no path left that discards a step event:

    - `@(initial_step or final_step)` **composes** into `if (initial_step() || final_step())`.
      That is what an event trigger list means, and it is sound here only because both halves
      are solver knowledge answerable at any evaluation. A list mixing in a scheduled event
      (`initial_step or cross(...)`) is still refused -- that is real trigger-list composition
      and needs the fired flag to reach the composed condition.
    - The **analysis-filter** form is refused at parse time, not analysis-gated. A filter says
      "not in this analysis", so discarding it runs the body precisely where the model excluded
      it: wrong in every analysis, which is the project's own test for which tier a refusal
      belongs in.
    - Anything else naming a step event is refused with a message saying which forms are honoured.

  **A limitation this work surfaced rather than introduced, now stated where it will be read.**
  `is_initial_step` is set on exactly one transient evaluation -- the seed assemble at `tstart`,
  which establishes state history and is never *solved*, `x0` being the caller's initial
  condition. So an `@(initial_step)` body influences committed state (the reason the flag was
  added, 2026-08-06) but changes no recorded point. `@(final_step)` is asymmetric with it as of
  0.9.8, its timepoint being re-solved. Making them symmetric means re-solving the run's first
  accepted timepoint, which changes what a supplied initial condition means -- deliberately not
  done here, and recorded in the roadmap rather than left for someone to rediscover.

  Corpus cost: none. The one occurrence in the corpus (`external/hisim2.va`'s
  `@(final_step("tran"))`) sits inside a ``ifdef` block that is not enabled, so it never
  reaches the parser; 113/132 either way.

  737 tests, 27/27 golden circuits, corpus 113/132 (95/99 self-contained), clippy and fmt clean.


0.9.8 — 2026-09-07
------------------
`@(final_step)` works, and stops being refused in transient. It is `initial_step`'s mirror in
the frontend -- desugared to a guarded `if`, lowered to `va_ir::Builtin::FinalStep`, reading a
new `va_abi::AnalysisCtx::is_final_step` (Interface beta, additive) -- and the entire difficulty
is on the consumer side: a driver knows its first evaluation before making it and its last one
only after the run has ended.

  So the integrator re-solves the last accepted timepoint with the flag set, the same way it
  re-solves a timepoint where a `cross` fired, and for the same reason: a body writing a
  variable that feeds a contribution changes the equations, and recording the pre-body solution
  would report a point at which the model's own statements do not hold. Knowing *which* point
  is last needs no lookahead -- the loop runs `while t < tstop` and clamps its landing to
  `tstop`, so the step being accepted ends the run exactly when its landing time does.

  The re-solve is **probed, not assumed**. `newton_step` applies its update before testing
  convergence, so re-solving every run's last point unconditionally would move it by a step's
  worth of round-off in exchange for nothing. Two assembles at the already-accepted point say
  whether any instance's stamps actually change when the flag is set. Cost: two extra `load`
  calls per run. Measured, not asserted: `cargo xtask validate` output is byte-identical to
  0.9.7+1's across all 27 gates.

  `is_final_step` is `true` in DC, AC and noise, so a *swept* DC runs the body at every point.
  That is the rule `is_initial_step` already follows -- each point is its own static solve, not
  a step within one -- and it is a stated limitation rather than the LRM's reading of a sweep.
  Two further limits: bare form only, and a run with no accepted step (`tstop <= tstart`)
  reports no final step, its only point being the unsolved seed.

  [Corrected in 0.9.9: this entry originally said a compound `initial_step or final_step` was
  "still refused". It was not -- it was discarded, and its body ran at every timepoint. See
  0.9.9's entry, which closes that and the analysis-filter form with it.]

  `va-cli`'s transient refusal of `@(final_step)` is gone with the reason for it;
  `initial_instance`/`initial_model` are the last two triggers still discarded and still
  refused there. Cost of that: nothing measurable -- the corpus scan does not run transient, and
  the count is steady.

  733 tests, 27/27 golden circuits, corpus 113/132 (95/99 self-contained), clippy and fmt clean.

0.9.7 — 2026-09-06
------------------
`@(above(...))` works, and it is not the one-sided `cross` it looks like. Per LRM 5.10.2 it
"also triggers during initialization or dc", which is the whole reason the construct
exists: a signal already past its threshold never crosses it, so a `cross` on it never
fires at all -- the LRM's own sample-and-hold example turns on exactly that. Implementing
only the transient half would have reproduced the bug the construct was invented to avoid.

  So a static solve had to grow events, having had none: va-core gains
  `mna::assemble_with_events`, `newton::solve_with_events` and
  `dc::operating_point_with_events`, all additive -- the existing entry points pass an
  empty set and behave exactly as before. The DC path is two-phase and iterates to a fixed
  point, because which events fire is a property of the solution while the bodies they
  guard change the equations that produce it.

  Interface beta: `monitor`'s `dir`/`tol` arguments folded into one `CrossSpec` carrying
  `at_initialization` too. The method took `dir` at 0.9.2 and `tol` at 0.9.6, so a third
  widening in four versions was the signal to stop widening. `FiredEvents` moved into
  va-abi, both consumers now sharing one shape.

  `above` and `absdelta` were added to RESERVED_WORDS, where LRM Table B.1 has them and
  this lexer did not. Safe: all 24 corpus occurrences of `above` are in comments ("the
  above copyright notice") and `absdelta` appears nowhere.

  Bare form only; `absdelta` and compound triggers remain refused.

  729 tests, 27/27 golden circuits, corpus steady at 113/132, clippy and fmt clean.


0.9.6 — 2026-09-06
------------------
`cross`'s `time_tol`/`expr_tol` are honoured, by a bracketing retry loop. A candidate step
that reveals a crossing it has overshot by more than the requested tolerance is rejected
and re-taken, aiming just past the interpolated crossing, through the same retry path the
LTE controller already uses. Aiming past rather than at the crossing is deliberate: the LRM
requires the event to fire after it, and landing a hair before would hide it.

  `EventSink::monitor` gained a `CrossTol` argument to carry the request. A signature
  change rather than a defaulted companion, for the reason the analysis context was one --
  a consumer that ignores a tolerance is silently failing to honour something the source
  asked for, so no implementor should be able to miss it.

  Measured convergence: ~70 ulps of the timescale -- a 1e-18 s tolerance really is met at
  t = 83us, where f64 spacing is ~1.4e-20 s. Below that spacing it cannot be, and the count
  is reported through `Waveform::unresolved_events` and warned about at the end of the run,
  rather than quietly missed. The blanket compile-time warning from 0.9.5 is gone, being
  no longer true.

  A site that requests no tolerance never brackets, so every pre-existing run is
  bit-identical: 27/27 golden circuits unmoved.

  724 tests, 27/27 golden circuits, corpus steady at 113/132, clippy and fmt clean.


0.9.5 — 2026-09-06
------------------
Stop dropping event arguments. The parser kept only the first two arguments of
`cross`/`timer` and silently discarded the rest, which included `enable` -- whose entire
job is to switch the event off, so a model that disabled an event got it firing anyway.
All arguments now reach elaboration, which interprets them positionally per event kind
and rejects a count the LRM does not define.

  `enable` is honoured: a disabled site registers nothing, so it cannot fire, and it is
  re-evaluated every accepted timepoint since it may switch during a run.

  `cross`'s `time_tol`/`expr_tol` are recorded on the IR and **warned about**. This engine
  fires at the accepted timepoint ending the bracketing step, so resolution is set by the
  timestep rather than by the requested tolerance -- a model asking for 1ns on a 2us step
  gets 2us. Carrying them means the bracketing retry loop that fixes this needs no further
  interface change. A `timer`'s `time_tol` raises no warning: the LRM asks for a timepoint
  within it and the integrator lands exactly, so it is already satisfied.

  Fixed along the way: with `enable` honoured, a disabled site stops reporting, and the
  consumer had been reading "no report" as a value of 0.0 -- which would compare against
  whatever the site last reported and fire the event precisely because it was switched off.
  Unreported slots are now distinct from zero.

  722 tests, 27/27 golden circuits, corpus steady at 113/132, clippy and fmt clean.


0.9.4 — 2026-09-06
------------------
`@(timer(...))` works, and the IR's event sites are unified. `va_ir::Module::cross_sites`
becomes `event_sites: Vec<EventSite>` with `Cross`/`Timer` variants and `Expr::CrossFired`
becomes `EventFired`, so slot numbering is one flat space across event kinds -- the
consumer's fired-flag buffer indexes it and must not care which kind claimed a slot.
Interface beta gains `EventSink::timer(slot, next)`, defaulted to forward to `breakpoint`:
a breakpoint only says "stop here", while a firing must say which event fires there.

  A model re-registers its next occurrence at every accepted timepoint, so it stays
  stateless about its own schedule -- the arithmetic is a pure function of
  (start, period, now). Period defaults to 0, the LRM's "fire once".

  Stated limitations: bare form only (a compound `initial_step or timer(...)` is still
  refused, as are `above` and `absdelta`); an occurrence landing on the run's *initial*
  timepoint is not delivered, that point being a seed rather than a solved step; tolerance
  arguments are parsed and discarded.

  718 tests, 27/27 golden circuits, corpus steady at 113/132, clippy and fmt clean.

Road to 1.0
-----------
Tracked in docs/roadmap.md; listed here so the release log is self-contained.

  [ ] Ship and test the executable across platforms. Today the workflow is `cargo run -p
      va-cli -- sim ...` from source on the Windows development machine (docs/workflow.md).
      1.0's deliverable is the compiled `va-cli` binary built from the tagged release, and it
      must be run and validated (`cargo xtask validate` figures, not "it builds") on several
      different computers and operating systems -- at least Windows, Linux and macOS -- with
      the machines and results listed in the 1.0 release entry. docs/workflow.md is then
      rewritten for the binary. Added 2026-09-11.

  [ ] Analog events. `@(initial_step)`, `@(cross(...))`, `@(timer(...))`, `@(above(...))`
      and `@(final_step)` all work as of 0.9.8, and an `or` list of the two step-scoped
      events composes as of 0.9.9. Still refused: `absdelta`, `last_crossing`, and any
      compound trigger mixing in a scheduled event (`initial_step or cross(...)`) -- that
      last one is real trigger-list composition and needs the fired flag to reach the
      composed condition.
      See roadmap "Analog events: what exists, and what each one still needs".

  [ ] absdelay / laplace_* in transient. Currently refused rather than folded (as of
      0.9.0), which is honest but not implemented. Lifting the refusal is
      docs/proposals/absdelay.md stage 2.

  [ ] Decide the sparse-solve question for the shipped configuration. The production
      path is dense LU; the project's own benchmark measured sparse winning 12-33x
      above ~20 nodes. **The decision is recorded** (roadmap, 2026-08-31): do not build
      sparse now, the trigger is circuit size rather than the calendar. What is still
      owed here is the other half of this item -- stating the circuit-size limit in a
      release entry, which no entry yet does.

  [x] Close the remaining expired-premise items. $mfactor from a deck's `m=` (0.9.11),
      $simparam answered during the solve (0.9.12), and $limit's model-declared junctions
      (0.9.13) are all done. The standing review itself does not close -- what is left on
      the roadmap's "Expired premises" list is two premises that have **not** expired
      ($rdist_* needs an RNG this engine has none of; I(<port>)'s narrow elaboration
      restriction is a refusal, not a fold), recorded there so they are not mistaken for
      gaps, plus a pointer into the analog-event section where that family is tracked.
