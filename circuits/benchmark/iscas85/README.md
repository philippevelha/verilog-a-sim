# ISCAS'85, starting with c17

> **Rule (the user's, 2026-09-23): build an ISCAS benchmark from the cells we already have** —
> the c7552 library's (`nand2`, `not1`, `and2`–`and4`, `nor2`–`nor4`, `or2`–`or4`,
> `xnr2v0x1`) — and when a netlist needs a gate the library lacks, **compose it from those
> cells** rather than writing a new one: a buffer is two inverters, a 4-input NAND an `and4`
> and an inverter, and so on (`gen_iscas.py`'s `COMPOSED` table). c17 and c432 follow it.

The ISCAS'85 combinational benchmarks as transistor-level PSP103 circuits, in the style of the
c7552 deck in `external/benchmarkExt/iscas85_benchmark_circuit/` (generated by `spicegen.pl`,
UIC VLSI group): every gate a `.subckt` of `N`-line PSP103 devices (ngspice's OSDI element),
every net an RC `.subckt`, the PSP103 model cards pulled in by `.include`, Vdd = 1.8 V.

| file | what |
|---|---|
| `c17.net` | `.op`, inputs 1 2 3 6 7 = 1 0 1 0 1 |
| `c17_tran.net` | `.tran 1p 12n`, the five inputs pulsing at periods 2–10 ns |
| `gen_c17.py` | writes either deck, any input vector (`python … gen_c17.py <out> op 10101`) |
| `check_c17.py` | the truth-table check (all 32 vectors) and the transient check |
| `c432.bench`, `c432.net` | c432's netlist, and its deck for one vector (below) |
| `c499 c880 c1355 c1908 c2670 c3540 c5315 c6288 c7552 .bench` | the rest of the suite (2026-09-26, Road to 2.0 item 1), each with its provenance and cross-check in its header |
| `c499.net`, `c880.net`, `c1355.net`, `c1908.net`, `c2670.net`, `c3540.net`, `c5315.net`, `c6288.net`, `c7552.net` | `.op` decks for one seeded vector each (seed = the circuit number) |
| `crosscheck_bench.py` | compare two copies of a circuit (`.bench` or gate-level `.v`): gate counts by type and the function on 4 096 random vectors, I/O matched by position or by signal number |
| `c432_tran.net` | `.tran 1p 1n`, all 36 inputs pulsing — a c432-size transient for measuring the transient solve (`docs/proposals/transient-solve.md`); 1 ns, not 12, because it runs for many minutes |
| `c432_seq.net` | `.tran 1p 10n`, a vector sequence: five seeded vectors, 2 ns each, every input switching through a 50 ps PWL edge (Road to 2.0 item 2, below) |
| `gen_iscas.py`, `check_iscas.py` | any `.bench` to a deck (`tran [<tstop>]` for a transient, `seq <T> <n> [<seed>] [<edge>]` for a vector sequence); check an `.op` against the logic, or a transient (`check_iscas.py tran <bench> <output>`: every settled sample of every reported gate output) |

**c17** is the suite's smallest circuit: six NAND2 gates, five inputs, two outputs —
`10=NAND(1,3) 11=NAND(3,6) 16=NAND(2,11) 19=NAND(11,7) 22=NAND(10,16) 23=NAND(16,19)`. The `nand2`
subcircuit is c7552's, verbatim. The wires use c7552's element values (2.080806 fF per pin,
2.224404 Ω per segment) as a star per net, driver pin to each load pin; c7552's generator also
builds trees, so this is the same style, not its output.

## Results (2026-09-23, 1.11.0, release build, i7-1185G7)

24 PSP103 devices, 81 devices after flattening, **420 unknowns** (30 nets + 390 internal rows):
sparse LU under the default solver.

- **`.op`, all 32 input vectors: 192/192 gate outputs correct.** Highs within 8 µV of the rail
  (worst 1.799992 V), lows at most 25.3 µV. 0.9–1.3 s per vector, whole process.
- **`.tran`, 12 ns at a 1 ps step: 13 466 points in 4.1 min.** Every settled sample of both
  outputs (5 528, over 11 distinct input vectors; "settled" = no input edge in the last 0.5 ns)
  matches NAND logic; worst high 1.799713 V, worst low 0.47 mV. The pre-flight estimate said
  0.08–2.4 min: it undershoots by ~1.7×, as it does for compiled-model circuits generally
  (`docs/validation.md`).

No golden reference: the project's oracle, QSPICE, has no PSP103 Verilog-A model set up here, so
the check is the logic function, not a waveform comparison.

## Running it

```
cargo run --release -p va-cli -- sim circuits/benchmark/iscas85/c17.net \
    --model benchmark/models/psp103/psp103.va
python circuits/benchmark/iscas85/check_c17.py truth target/release/va-cli.exe
```

Needs `benchmark/models/psp103/psp103.va` and the c7552 drop's model cards, both committed under
`benchmark/` since 1.28.0+1 (their origin and licenses: `benchmark/README.md`).

## c432 (1.12.0)

`c432.bench` is the standard netlist (provenance in its header: fetched, then checked gate for gate
against an independent gate-level Verilog copy). `gen_iscas.py` turns any `.bench` into a deck in
the same style as c17; `c432.net` is its output for one input vector (seed 432). c432 needs gates
c7552's library lacks — 4-input NAND, XOR, 8- and 9-input AND — so they are **composed** from its
cells (NAND*n* = AND*n* + NOT, XOR = XNOR + NOT, AND8 = 2·AND4 + AND2, AND9 = 4·AND3): the logic
is exact, the timing is not a single cell's.

**Size:** 160 gates, 910 PSP103 devices, 2 458 devices after flattening, **15 416 unknowns**
(819 nets + 14 597 internal rows), sparse LU.

**Correctness, `.op`:** five input vectors; the first checked on the 7 primary outputs, the other
four on **all 160 gate outputs — 640/640 correct** (`check_iscas.py`). Highs ≥ 1.799989 V, lows
≤ 25.3 µV.

**Convergence** needed a new rescue tier (`va_core::dc`, `RESCUE_NODE_STEP`): the plain solve,
the `gmin` ladder and the damped ladder all failed, stuck on the internal nodes of the 4-high NMOS
stacks inside the composed NAND4s, which only leakage sets while a lower device is off. Capping
each node's Newton step at 0.5 V solves it.

### Wall time (release, i7-1185G7, `.op`, one run each)

| run | result | wall |
|---|---|---:|
| c432, 1.11.0 (plain → ladder → damped ladder) | singular, all tiers failed | 7.1 min |
| c432, experiment: every tier capped at 0.5 V | solves | 3.8 min |
| c432, 1.12.0 tiers (… → capped ladder → damped), vector seed 432 | solves | 6.9 min |
| c432, 1.12.0, four more vectors | all solve | 3.2, 6.3, 3.5, 5.8 min |
| c432, 1.12.0, vector seed 432 again (profiled) | solves | 2.9 min |
| c17 (420 unknowns) | solves | 1.1 s |

**Run-to-run spread is large:** the same deck and binary took 6.9 min once and 2.9 min later,
so on this laptop a single wall time is good to about 2×. Read the table as ranges, not points.

**Where the time goes** (profiled run, 558 Newton steps): assembly — evaluating the 910 PSP103
instances and stamping — **218 ms per step, ~70%** of the run; the sparse LU solve **88 ms per
step (median 82, max 192), ~28%**; ~55 000 nonzeros; the pattern grew 6 times (a symbolic
refactorization each). About 0.24 ms per PSP103 instance per iteration. An earlier trace read
760 ms per step, probably while a stray build competed for the CPU — not confirmed. The
pre-flight estimate quoted 44–719 ms, off by ~250–600×: it is per Newton loop on linear circuits
and cannot see a rescue.

**Not run (at 1.12.0): a c432 transient.** From the figures above, `.tran 1p 12n` would be
~13 000 points × a few Newton iterations × ~0.3 s per step, i.e. **3–4 hours**. Recorded as an
estimate, not run. It has since been run: `c432_tran.net` (1 ns) at 1.26.0, and the vector sequence
at 1.28.0 — see the end of this file.

## c7552 (not attempted)

The deck on disk parses with 1.11.0's `.subckt`/`.model`/`N`/`.include` support, but it is
~250 000 unknowns (14 942 PSP103 devices), 50× the largest device circuit solved so far (5 286
unknowns, `docs/validation.md`). At c432's measured ~0.24 ms per PSP103 instance per Newton
iteration, the assembly alone of one c7552 iteration would be ~3.6 s, so even an operating point that converged in
the ~300 iterations c432's took would be ~20 minutes.

One thing noticed in the c7552 deck and not yet explained: some net subcircuits (`netg10`,
`netg182`, …) contain only pin capacitors and no resistor, which leaves their pins unconnected to
each other.

## The rest of the suite (2026-09-26, 1.27.0) — Road to 2.0, item 1

**Netlists.** c499, c880, c1355, c1908, c2670, c3540, c5315 and c6288 fetched from the same
repository as c432; c7552 (absent there) from the Tallinn University of Technology archive
(`pld.ttu.ee/~maksim/benchmarks/iscas85/bench/`). Every one agrees with an independent copy —
same gate counts by type (the published ISCAS'85 figures) and the same function on 4 096 random
vectors (`crosscheck_bench.py`); each header says which copy and how. Two discrepancies, both
in the *other* copy, and resolved:

- **c1355:** the gate-level `.v` in `santoshsmalagi/Benchmarks` drives all 32 outputs through
  inverters where the `.bench` has buffers — every output inverted. The `.bench` is right: c1355
  is c499 with its XORs expanded into NANDs, and it computes exactly c499's function (32/32
  outputs); TTU's copy agrees with it.
- **c2670:** the `.v` pads the circuit with 76 extra buffers (1 269 gates, not 1 193) and keeps
  the original signal numbers where this `.bench` renumbers them; TTU's copy matches this
  `.bench` input for input and the `.v` signal for signal — one function, three copies.

A third check of c7552, against the logic of the transistor-level deck in
`external/benchmarkExt/` (spicegen), is **inconclusive**: that deck renumbers every signal, and
pairing its 207 inputs with the `.bench`'s by order matches 2 207 of 3 512 internal signals — a
partial input correspondence, not recovered.

**Cells.** Five gate widths the suite needs and the c7552 library lacks are composed from its
cells (`gen_iscas.py`'s `COMPOSED`, fewest cells that are exact): AND5 = AND4 + AND2,
NAND5 = AND4 + NAND2, NAND8 = 2 x AND4 + NAND2, OR5 = OR4 + OR2, NOR8 = 2 x OR4 + NOR2. Every
composition in the table, old and new, was checked against its gate on all 2^n input
combinations; `c432.net` regenerates unchanged.

## c432 transient against its logic (2026-09-27, 1.28.0) — Road to 2.0, item 2

`c432_seq.net` (`gen_iscas.py c432.bench c432_seq.net seq 2n 5`, seed 432): five vectors held
2 ns each, all 36 inputs moving to the next vector through a 50 ps PWL edge at once, `.tran 1p 10n`.
**11 570 points in 46.8 min (8 threads); `check_iscas.py tran`: 1 196 800 settled gate-output
samples over the 5 vectors, all correct, 7/7 primary outputs among them** (worst high 1.792 V,
worst low 2.6 mV).

It needed three integrator changes (release.txt, 1.28.0): sources report their corners as
breakpoints and the integrator restarts there (backward Euler, history cleared) — before, the
trapezoidal rule rang at the 2 ns corner and the run died of timestep underflow 0.1 ps after it;
breakpoints closer than the minimum step merge; and the floor rule applies where PSP103's Newton
gives out, not only at the minimum step.

## The suite at 2.24.2 (2026-10-14, release build, Xeon 2.8 GHz, 4 vCPUs)

Every deck once, one at a time on all 4 threads (`--threads 4`), default settings; the two
transients also with `--bypass`. Wall time and peak resident memory of the `va-cli` process.
Each `.op` is checked against its `.bench` logic (`check_iscas.py`, the seeded vector it was
generated for); `c17_tran` by `check_c17.py tran`. `c17.net` and `c432_tran.net` have no check
(no `.bench` for c17; `c432_tran` is a 1 ns timing deck whose inputs never settle for the 0.5 ns
`check_iscas.py tran` needs). For reference, 2.4.0+1's times (2026-10-02) were measured on
another, 8-thread machine, so read the two columns as roughly comparable, not to better than ~2×.

- **Every operating point is correct**, c432 to c7552, and so is `c17_tran` with and without
  bypass (5 636 settled output samples over 11 input vectors, all correct).
- **Bypass is the speed-up that works here: 1.7× on `c17_tran`, 1.4× on `c432_tran`**, with the
  same timepoints. On `c432_tran` it moves no node by more than 1 µV against the plain run (8 099
  nodes, 201 times).
- **The operating points are where they were at 2.4.0+1**, on a slower 4-vCPU machine. Most of
  their time is the `gmin` rescue (~300 Newton iterations, 1.27.0+5).

**Two settings that do not help on ISCAS, measured while preparing this table** (both
opt-in; neither is on by default):

- **`VA_JIT=on` is a net loss.** It compiles the model's statically scheduled program to
  machine code once per distinct parameter set (`va_codegen::SharedModel`), serially, ~0.8 s
  each for PSP103. These decks have 6-15 sets (one per transistor size and card), so it costs
  5-12 s up front and saves almost nothing: c17 0.3 -> 1.9 s, c880 12.0 -> 20.6 s, c2670 with
  collapse 82.4 -> 92.4 s (13 sets, ~10.7 s of compile). At this size the time is in the sparse
  solve and per-step bookkeeping, not in device evaluation (as 2.18.0+4 found at 70 k unknowns).
- **`VA_COLLAPSE=on` breaks down from c1908 up.** It merges PSP103's shorted source/drain nodes
  (c1908: 62 055 -> 10 731 unknowns) and helps the small circuits (c432 9.0 -> 6.0 s, c1355
  16.7 -> 13.9 s, though memory already grows: c1355 0.73 -> 1.29 GB), then gets worse: c1908
  27.1 s / 1.2 GB -> 65.2 s / 7.2 GB, c2670 48.3 s / 1.8 GB -> 85.5 s / 8.0 GB, and c3540 was
  killed for memory at 13.6 GB. The smaller matrix
  factors with far more fill: with the block-triangular path off (`VA_BTF=off`), the collapsed
  c1908 ran past 10 minutes against 71 s with it on. Not diagnosed further (the fill was not
  measured); collapse's own check (2.21.0+1) never ran the slow ISCAS decks. Until it is
  understood, keep collapse off above ~10 k unknowns.
